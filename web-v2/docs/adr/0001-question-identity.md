# ADR-0001 · 题目身份策略

- 状态：**已采纳（Accepted）** 2026-11-16，由项目负责人确认
- 日期：2026-11-16
- 决策者：项目负责人
- 相关：`项目规划/T0-8-旧数据契约清单.md` §2、`02-S1` T1-2、`web-v2/packages/core/src/ids.ts`

---

## 背景

旧版没有持久化 ID。`data.json` 里只有 `type` + `no`，`q_key` 是运行时拼出来的 `type + "-" + no`（`_build/template.html:756`）。而 `no` 是 **Markdown 解析顺序号**，不是人工指定的稳定编号。

后果在 T0-8 已经写明：题库里插一道题，后面所有 `no` 整体位移，**同一条历史记录会指向另一道题，且不报错**。这是本次通用化最危险的一处静默错误——用户已经积累了 91 条掌握记录、43 条错题和若干模考成绩，全部挂在 `q_key` 上。

同时有两个反向约束：

1. **ID 不能由内容算出来**。若用题干哈希做 ID，改一个错别字就等于换了一道题，历史正确率会断成两段。
2. **ID 不能是纯随机 UUID 且无人维护**。题库包是人工可读的内容文件，UUID 会让 diff 无法审查——"这 3 处改动是改了题还是加了题"看不出来。

## 决策

采用**人工冻结的语义 ID + 内容哈希作修订号 + 冻结映射表承载旧键**三者分离：

```ts
// 1) 身份：语义 ID，写进内容文件，一旦分配永不复用、永不改名
questionId = `${bankId}:${type}:${seq}`
// 例：javaweb:single_choice:001   javaweb:code_blank:003

// 2) 修订：内容哈希，由构建期计算，不手写
revision = sha256(规范化后的题面 + 选项 + 答案 + 解析).slice(0, 12)

// 3) 旧键：一次性迁移时写入，之后只读
legacyKeys = ["choice-1", "choice-1@legacy-javaweb-20261116"]
```

配套三条硬规则：

- **新增题目分配新 `seq`**，取当前该题型最大值 +1，**不复用已删除题目的编号**（避免旧记录串到新题上）
- **改内容只升 `revision`，不动 `questionId`**
- **删除题目保留 `questionId`，从内容包里移除**，历史记录因此仍能解析出"这道题已下线"，而不是指向别的题

另外生成一份**冻结映射表** `packages/content/javaweb-final/legacy-map.json`：

```jsonc
{ "javaweb-final": { "choice-1": "javaweb:single_choice:001", /* …147 条 */ } }
```

映射表**在迁移时一次生成、人工确认后入库**，此后不再由脚本重算。题库文本一旦变化，构建期必须报"legacy-map 与当前题库不一致，请人工确认"，而不是自动重映射。

## 备选方案与不选的理由

| 方案 | 为什么不选 |
| --- | --- |
| 纯 UUID（`crypto.randomUUID()`） | 内容文件 diff 不可读；换一台机器重新导入会生成新 UUID，幂等性直接失效 |
| 内容哈希作 ID | 改错别字 = 换题，历史记录断裂。这正是我们最想避免的静默错误 |
| 继续用 `type-no`（现状） | 顺序号漂移问题原样保留，等于把风险带进新版 |
| 全局自增整数 | 多题库合并时会撞号；无法从 ID 看出属于哪个题库 |

## 后果

**好处**

- 历史记录与新题库的绑定是**可审计的**：改题不换 ID，加题不串号
- `legacy-map.json` 独立成文件，`git diff` 能直接看出"哪条旧记录被映射到了哪道新题"
- `revision` 让 S4 的"按修订统计正确率"成为可能，且不需要重构

**代价**

- 新增题目必须人工或脚本分配 `seq`，不能随手插入
- 迁移脚本多一步"读冻结映射表"，不能用"按顺序 zip"这种图省事的做法
- 题库文本改动会触发 `revision` 变化，历史 Attempt 的 `questionRevision` 会与当前 revision 不一致——这是**特性不是 bug**，S4 需要按"作答时的那一版"判分

## 判定这条决策是否成功

S1 收尾时检查三条，全部满足才算定案：

1. 迁移连续执行两次，`questionId` 与输出逐字节一致
2. 在题库里插入一道新题并重建，**已有 147 条的 `questionId` 全部不变**
3. 改一道题的解析并重建，`questionId` 不变、`revision` 变化、`legacy-map.json` 无差异

第 2 条是关键：它正是旧版会失败的那个场景。
