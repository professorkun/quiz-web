## 1. 这份规划怎么用

| 目录文件 | 作用 | 什么时候读 |
| --- | --- | --- |
| `00-总览-阶段地图与阶段门禁.md` | 全局规则：阶段依赖、通用门禁、DoD、验收写法、Git 映射、风险台账 | 每次开工前 |
| `01-S0-…` ～ `10-S9-…` | 单阶段计划：目标、范围、任务、交付物、验收、门禁、风险、回退 | 进入该阶段时逐条执行 |
| `11-模板-新增阶段计划模板.md` | 新增阶段（如 S7 拆出的子阶段）时复制使用 | 需要加阶段时 |

**使用纪律（三条）**

1. **一次只计划一个阶段**：S0–S2 已细化到任务级；S3 之后只锁定目标与验收，任务清单在进入该阶段时再细化。这是滚动式规划（rolling wave），避免对远期工作做会立刻作废的细节设计。
2. **验收标准先于编码**：每个阶段的"验收标准"在动手写第一行代码前定稿；验收标准在验收时补写的，描述的是"做成了什么"，不是"需要什么"。
3. **阶段门禁是硬门**：上一阶段门禁未全绿，不进入下一阶段；确有例外，必须在 `00` 文件 §9 变更登记里写明理由、风险与补救项。

## 2. 项目目标与成功标准

**一句话目标**：把"JavaWeb 期末复习页面"升级为"可以装入任意学科题库，并持续记录学习过程的通用刷题应用"。

**项目级成功标准（V1，S6 结束时判定）**

| 编号 | 成功标准 | 判定方式 |
| --- | --- | --- |
| SC-1 | 两个不同题库可在同一应用内切换，学习记录互不串 | 端到端用例：JavaWeb + 演示题库各答 5 题 |
| SC-2 | 游客不登录即获得完整闭环：作答→解析→错题→复习→统计 | 清空浏览器存储后全流程手测 |
| SC-3 | 数据零静默丢失：147 题、89 个代码空位、旧错题记录全部可迁移 | 迁移报告 + 数量对账 |
| SC-4 | 旧版功能对等：题库、刷题、模考、错题、知识、我的六模块无缺失 | 逐条对照用例 |
| SC-5 | 可发布、可回退：CI 双绿、真实云端读写通过、回退步骤演练过 | Release 记录 |
| SC-6 | 领域逻辑与平台无关：判分/选题/复习只在 `packages/core`，Node 环境可测 | 单测 + 依赖检查 |

## 3. 阶段地图与依赖

  S2 --> S3[S3 多题库与本地记录]

| --- | --- | --- | --- | --- | --- |
| S0 | 建立 Git 基线、旧版维护机制与迁移准备 | 无 | `chore/git-init` → `main` | `legacy-javaweb-20261116` | M |

| S4 | 错题、复习与统计闭环 | S3 | 同上 | `s4-review-loop` | M |

| S6 | 云同步、PWA、可访问性与发布切换 | S5 | `general-dev` → `main` | `general-v1.0.0-rc.1` / `general-v1.0.0` | L |
| S7 | V1 之后的增强路线 | S6 | `feat/general-*` | 按子项打 | 按子项 |
| S8 | Android（Capacitor 套壳） | S6 | `feat/android-*` | `android-v1.0.0` | M |
| S9 | 微信小程序 | S8 | `feat/weapp-*` | `weapp-v1.0.0` | L |

**工作量口径**：S = 1–2 个工作块，M = 3–5 个，L = 6–10 个。1 个工作块 = 一次可交付小结果的专注开发（约 2–4 小时），**不排日历日期**——单线程个人项目按阶段推进比按日期推进可靠，日期在阶段启动时才填。

**顺序约束（不可调换的因果链，来自方案 §12）**

1. 先 Git 基线，再双线开发；
2. 先稳定数据契约，再写页面；
3. 先本地闭环，再接云；
4. 先功能对等与最终增量对账，再替换旧版；
5. 多端顺序 Web → PWA → Android → 小程序，不并行。

## 4. 通用门禁：任何阶段放行前必过的四道检查

| 门禁 | 问题 | 不通过的表现 |
| --- | --- | --- |
| **G1 数据** | 题目、记录、配置有没有数量对账与错误定位？ | 静默丢题、重复 ID、迁移后题数对不上 |
| **G2 功能** | 本阶段承诺的能力是否每条都有可执行验证？ | "点了一下没问题"式验收 |
| **G3 工程** | 单测、构建、CI、无控制台未处理异常？ | 靠人工记忆保证正确性 |
| **G4 可回退** | 出问题能否退回上一个可用状态且不丢数据？ | 只能"往前修"，不能退 |

**阶段收尾动作（固定顺序）**

1. 跑本阶段验收清单 → 2. 记录结果到阶段文件 §12 → 3. 更新 `00` §8 阶段状态表 → 4. 打阶段标签 → 5. 把遗留问题写入 S7 待办，而不是塞进本阶段尾巴。

## 5. 通用 Definition of Done（每阶段默认适用）

任何一项工作要标"完成"，需同时满足：

- [ ] 验收标准逐条通过，且证据可复现（命令、截图、测试名或对账数字）
- [ ] 新增/变更的领域逻辑有单元测试，且测试不依赖 DOM、React 或网络
- [ ] 数据类型变更同步了 Schema 与校验，非法输入给出具体题目与字段位置
- [ ] 无静默失败：异常有提示、有日志，不吞错
- [ ] 相关文档（README / 迁移报告 / 阶段文件）已同步，未留"以后补"
- [ ] 变更已提交，提交信息符合 Conventional Commits，并走 PR 进入目标分支
- [ ] 未引入方案 §1 明确排除的能力（OJ、AI 出题批改、班级权限、社区、实时协作、复杂自适应算法）

**阶段级 DoD 的加严项**：S1 起追加"`packages/core` 无 React/Dexie/`wx.*`/DOM 依赖"；S4 起追加"统计可由 Attempt 重算"；S6 追加"回退步骤演练过"。

## 6. 验收标准怎么写（本规划的统一约定）

三种格式按场景选，不强求统一，但必须满足四条硬要求。

**格式**

- **规则式**：适合可穷举的硬约束。例：`147 题分布必须为 62/45/27/8/5`。
- **检查单式**：适合交付物完整性。例：`六个题型均有渲染器 + 判分器 + Schema`。
- **场景式 Given / When / Then**：适合有交互状态的功能。例：
  > Given 游客已答错第 12 题，When 刷新页面并继续同一会话，Then 该题仍显示为答错状态、错题计数为 1、题序与选项顺序与刷新前完全一致。

**四条硬要求**

1. **用数字替换形容词**：不写"加载要快"，写"冷缓存下首屏内容 3 秒内可见"。
2. **一条只测一个行为**：出现三个以上 `And` 说明该拆成两条。
3. **必须覆盖三类不顺利场景**：空（新用户/零记录）、错（断网/超时/非法输入）、权限（未登录/登录过期/跨用户）。
4. **可由他人照文执行**：只读这条标准就能写出测试或手动复现步骤；做不到就是标准没写完。

## 7. Git 与协作映射

| 事项 | 约定 |
| --- | --- |
| 稳定分支 | `main` 始终可发布；只接受 PR |
| 新版集成分支 | `general-dev`，从基线 `main` 创建，S6 达标后合回 `main` |
| 旧版修复 | `fix/legacy-*` → PR 到 `main`，再合并回 `general-dev` |
| 内容更新 | `content/javaweb-*`，只改 Markdown 源文件，重新构建产物，不手改生成物 |
| 新版功能 | `feat/general-*` → PR 到 `general-dev` |
| 阶段标签 | 阶段验收通过后在 `general-dev` 打 `s{n}-<slug>` |
| CI | `legacy-ci.yml`（题量自检、可重复构建、旧版冒烟）与 `general-ci.yml`（TS、lint、Vitest、构建）双轨，互不阻塞 |
| 提交信息 | `fix(legacy): …` / `content(javaweb): …` / `feat(practice): …` / `test(migration): …` |
| 禁止 | 对共享分支 force push；手改生成后的 HTML；`git add .` 前不做敏感信息检查 |

## 11. 规划方法说明（为什么长这样）

- **骨架借 PRINCE2 的 Stage Plan**：目标与范围、产品描述、质量与验收、前置依赖、风险、控制与报告、容差——这套结构的好处是每个阶段都"自包含"，隔一个月回来只看单个文件就能继续干。
- **验收借 BDD 与 SMART**：Given/When/Then 保证可执行，数字替代形容词保证可判定，空/错/权限三类场景保证 bug 无处藏身。
- **不排日历、只排工作块**：个人单线程项目里，日期估算的误差主要来自"被打断"，而阶段门禁的收益来自"不带着隐患往前走"。所以用工作量等级 + 门禁，而不是甘特图。
- **不新增需求**：本规划所有任务与验收项均可追溯到方案 §9 的阶段任务与 §10 的验收条款；规划只做拆分、编号、排序与判定标准补全。
