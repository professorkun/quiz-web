## 1. 阶段目标

**目标陈述**：在微信内提供原生体验的刷题入口，UI 用小程序重写，**判分与选题一律调用 `packages/core`**；通过按需拉取题库与分包把主包控制在 2MB 内，并完成审核上架。

**可衡量目标**

| 编号 | 指标 | 目标值 | 验证方式 |
| --- | --- | --- | --- |
| G9-1 | 三项前置 | 域名白名单、登录打通、类目资质全部确认 | 前置验证记录 |
| G9-2 | 主包体积 | ≤ 2MB | 上传时体积报告 |
| G9-3 | 题库按需 | 147 题可按需加载，不进主包 | 分包配置 + 手测 |
| G9-4 | 逻辑复用 | 判分/选题全部来自 `core`，无副本 | 代码扫描 |
| G9-5 | 数据一致 | 登录后小程序记录与 Web 一致 | 双端交叉 |
| G9-6 | 审核通过 | 提审通过并发布 | 审核结果 |

## 2. 范围边界

**本阶段做**

- 三项前置验证（**先做，且是硬门**）
- `apps/weapp` 页面实现（UI 重写，逻辑复用）
- `weapp` 侧 `StorageAdapter`（`wx.storage`，注意单键 1MB / 总量 10MB）
- 题库按需拉取 + 分包策略
- 审核材料与类目描述

**本阶段不做**

- 不改云端架构以迁就小程序（方案明确：不通过就暂停）
- 不用 Taro/uni-app 提前重写 Web
- 不做三端并行
- 不复制判分/题库逻辑到小程序
- 不做小程序端独有的题库编辑等重功能

## 7. 验收标准

### A. 前置与包体

- [ ] 三项前置验证全部有通过证据（配置截图/实测记录/审核口径）
- [ ] 主包体积 ≤ 2MB（上传体积报告为准）
- [ ] 147 题可通过按需加载获取，未打进主包

### B. 功能与数据

- [ ] 五个入口可用：学习 / 题库 / 刷题 / 复习 / 我的
- [ ] 判分、选题、复习调度全部调用 `packages/core`
- [ ] 登录后小程序记录与 Web 端一致（错题、进度、成绩）
- [ ] `wx.storage` 接近上限时有提示与清理入口，不静默失败

### C. 审核

- [ ] 类目与描述符合要求，提审材料齐全
- [ ] 审核通过并发布成功

### D. 关键场景（Given / When / Then）

1. **按需拉取**
   Given 首次进入小程序、未缓存任何题库，When 选择 JavaWeb 题库，Then 题库被拉取并缓存，主包体积未变化。
2. **跨端一致**
   Given 在小程序答错第 8 题，When 在 Web 端打开复习页，Then 第 8 题出现在错题列表且复习间隔一致。
3. **存储上限**
   Given 本地缓存接近 10MB，When 再下载一个题库，Then 提示空间不足并提供清理选项（如清理已掌握题库缓存），不崩溃。
4. **登录链路**
   Given 首次进入小程序，When 点击登录并授权，Then `wx.login` 换取 session 成功，云端记录可读可写。

### E. 不可接受的情形

- 前置验证未做完就开始写页面
- 主包超限靠"删功能"临时应付（应为按需拉取）
- 小程序内复制一份判分逻辑
- 为适配小程序而改动云端架构
- 存储超限静默丢数据

## 9. 阶段特有风险与应对

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| 域名备案不可行 | 无已备案域名 | 前置验证即停，不投入开发 |
| 登录打不通 | code 换 session 失败且无解 | 前置验证即停；考虑仅做只读题库浏览 |
| 类目资质受限 | 教育类需资质 | 调整类目或暂停 |
| 主包超限 | 上传报体积超限 | 分包 + 按需拉取，禁止把题库打进包 |
| 存储上限 | 10MB 打满 | 缓存分级：题目按需、已掌握可清理 |
| 三端逻辑分叉 | 出现判分副本 | CI 检查 `core` 之外无判分实现 |

---

## 10. 回退方案

1. 暂停即回退：不发布小程序，Web / PWA / Android 不受影响。
2. 发布后回退：小程序后台下线，云端数据与 Web 共用，无需迁移。
3. 数据安全：小程序写入的均为标准 V2 记录，回退不产生孤岛数据。
