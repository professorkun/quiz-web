# T0-10 · 旧版云端读写验证方案

> 目的：确认「登录 → 写入 → **换账号读不到** → 回原账号仍在」这条链路真的成立。
> 为什么单独做：旧报告只证明"页面能显示"，那可能来自内存或 `localStorage`，**不能证明服务端写成功了**。`00` §8 把"云端验证通过是假通过"列为风险，这条就是拆它。
> 状态：**待执行**（需要两个可收短信的手机号）。

## 一、验证的三个动作（顺序不能改）

| 步 | 动作 | 看什么 | 通过标准 |
| --- | --- | --- | --- |
| **1 写入** | 用**账号 A** 登录（我的 Tab → 手机号 → 获取验证码 → 登录/注册）→ 模考 Tab 做一份卷并交卷 | 交卷后是否出现「✓ 已保存到云端，可在「我的」查看」 | 提示出现；「我的」里能看到这条成绩（含分数与时间） |
| **2 换账号读** | 我的 Tab → 退出登录 → 用**账号 B** 登录 → 看「我的」与「错题」 | B 的列表是空的还是有 A 的数据 | **必须为空**。若能看到 A 的成绩或错题 → **RLS 缺失/写错，属阻断级问题**，立即停止后续阶段 |
| **3 隔离确认** | 退出 B → 用账号 A 重新登录 → 再看「我的」与「错题」 | A 的数据是否还在 | 成绩与错题**仍在**。这一步才排除"其实是本地缓存"的可能 |

> 只做第 1 步不算验证。第 2 步没做 = 不知道数据是否串号；第 3 步没做 = 不知道数据是否真落库。

### 补充证据：RLS 对匿名生效（接口级探测）

用页面里本就公开的 `publishableKey` 作为 `x-wb-webapp-access-key`，不带任何会话，直接请求四张表：

```
GET {endpoint}/.cloud/database/rest/{table}?select=*&limit=3
```

| 表 | 结果 |
| --- | --- |
| `wrong_questions` | HTTP 200，`[]` |
| `quiz_mastery` | HTTP 200，`[]` |
| `exam_records` | HTTP 200，`[]` |
| `drill_progress` | HTTP 200，`[]` |

而同一时刻界面上 `quiz_mastery` 至少有 **91 行**（掌握进度 91/147）。**表非空但匿名读到 0 行 → RLS 确实按会话过滤，匿名拿不到数据。**

这是"必要证据"，不等于"账号 A/B 隔离已验证"：匿名被挡住的可能是"无 owner 的数据"，而 B 能否看到 A 的数据仍必须实测。
