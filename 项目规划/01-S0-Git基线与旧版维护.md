## 1. 阶段目标

**目标陈述**：让"当前这套旧版"从一堆本地文件变成一个有版本、可重现、可回退、可安全公开边界的工程基线；同时把新版的开发通道（`general-dev` + `web-v2/`）在不动旧文件的前提下建好。

**可衡量目标**

| 编号 | 指标 | 目标值 | 验证方式 |
| --- | --- | --- | --- |
| G0-1 | 远程仓库可重现旧版 | 克隆到新目录后能构建出与提交物一致的 HTML | 新目录 `git clone` + 跑构建脚本 + 比对 |
| G0-2 | 题量基线锁定 | 147 题，分布 62/45/27/8/5 | CI 检查脚本输出 |
| G0-3 | 旧版冒烟项 | 6/6 通过 | 冒烟清单逐条执行 |
| G0-4 | 敏感信息入库 | 0 处（令牌、手机号、云端密钥、学习记录导出） | `git log -p` 与暂存区双查 |
| G0-5 | 工作树干净 | `git status` 无未跟踪的业务文件 | 命令输出 |
| G0-6 | 新版通道就绪 | `general-dev` 存在且与 `main` 同基线，`web-v2/` 未被旧构建链引用 | 分支列表 + 构建一次旧版 |

## 2. 范围边界

**本阶段做**

- 仓库初始化、忽略规则、基线提交、标签、远程推送
- README 与文件职责说明
- 旧版 CI（构建 + 冒烟 + 题量自检）
- 敏感信息与内容版权边界检查
- 旧数据契约清单（`q_key`、云表字段、登录流程）
- 一次真实云端读写验证（有可用登录态时）

**本阶段不做**

- 不新建 `web-v2/` 的任何代码（只确定目录将存在，S1 才建）
- 不重构、不美化、不优化旧版任何逻辑
- 不删除根目录 `sdk.js`、不移动 `_build/`、不整理 `题库网页/`
- 不引入 NAS 备份（方案已定：阶段二再做，不阻塞上线）
- 不改动任何云端生产数据

```bash

# 先完成 .gitignore、敏感信息检查、旧版构建与测试，再暂存

git commit -m "chore: establish JavaWeb legacy baseline"
git tag -a legacy-javaweb-20261116 -m "Verified JavaWeb legacy baseline"
git remote add origin <你的仓库地址>
git push -u origin main --tags
git switch -c general-dev
git push -u origin general-dev
```

## 6. 验收标准

### A. 仓库与数据

- [ ] 新目录克隆后，执行构建命令可得与提交物一致的 HTML（字节级或结构级比对通过）
- [ ] CI 输出的题量为 **147**，且分布严格为 **选择 62 / 判断 45 / 填空 27 / 简答 8 / 应用 5**
- [ ] **89 个代码空位**在构建自检中被计数并输出
- [ ] 提交历史中不含：访问令牌、私钥、`.env*.local`、学习记录导出、云数据库备份、手机号
- [ ] 仓库内不存在 `web-v2/dist/`、`node_modules/`、日志与临时文件
- [ ] `.workbuddy/` 被忽略且**目录仍然存在**（未删除）

### B. 旧版可用性

- [ ] 本地打开旧版 HTML，六个 Tab（题库、刷题、模考、错题、知识、我的）均可进入
- [ ] 冒烟 6/6 通过，结果记录在案
- [ ] 发布入口未切换，用户侧使用方式与 S0 之前完全一致

### C. 工程与规范

- [ ] `legacy-ci.yml` 在 PR 上变绿；人为修改生成物后 CI 变红（证明检查有效）
- [ ] `main` 已开分支保护，要求 CI 通过
- [ ] `general-dev` 与 `main` 同基线
- [ ] README 可让一个没参与过项目的人完成"启动 + 构建 + 发布"

### D. 关键场景（Given / When / Then）

1. **可重现**
   Given 一个全新的空目录，When 克隆仓库并执行构建脚本，Then 生成的 HTML 与仓库内提交的产物内容一致，CI 判定一致。
2. **拦截误改**
   Given 有人直接手改 `JavaWeb期末题库.html` 的某个字符，When 提交并开 PR，Then `legacy-ci.yml` 失败并指出"生成物与源文件不一致"。
3. **阻止泄漏**
   Given 暂存区里混入一个含 token 的本地配置文件，When 执行提交前检查，Then 该文件被 `.gitignore` 排除或检查脚本报错阻止提交。
4. **不动旧文件也能加新版**
   Given 已建好 `general-dev`，When 在其中新建 `web-v2/` 空目录并提交，Then `main` 分支构建旧版的结果不受任何影响。

### E. 不可接受的情形（出现任一即判本阶段未通过）

- 为了让 CI 变绿而放宽题量检查或跳过冒烟
- 在 `main` 上直接堆新版代码
- 删除或移动旧文件以"顺便整理"
- 把 `publishableKey` 的"可公开"误解为"数据库可公开读写"，未核对 RLS 就宣布云验证通过

## 8. 阶段特有风险与应对

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| 首次提交夹带个人数据 | 暂存文件数远超预期 | 先 `git status` 逐项过，再 `git add` 指定路径而非 `.` |
| 误删"看起来冗余"的 `sdk.js` | CI 运行时兜底失效 | 按方案 §2.2：根目录 `sdk.js` 保留，不视为冗余 |
| CI 只校验产物不校验可重建 | 本地改产物后仍变绿 | 必须让 CI **从源文件重建后比对**，而非仅做语法检查 |
| 迁移映射草率 | S1 时发现旧记录无处安放 | T0-8 必须真的读一遍 `q_key` 与云表字段，不靠印象 |
| 云端"验证通过"是假通过 | 未登录/未真写库 | 只认"写入 → 换账号读取 → 隔离确认"三步齐全 |

## 9. 回退方案

本阶段不产生线上变更，回退成本最低：

1. 未推送前：`git reset --soft HEAD~1` 或直接删除 `.git` 重来。
2. 已推送但基线有问题：不 rewrite 历史，打新标签 `legacy-javaweb-2026xxxx-r1` 覆盖使用，旧标签保留作对照。
3. CI 误伤日常使用：CI 只做检查不阻断本地使用；必要时临时关 CI，但需在 `00` §9 登记。
4. 旧版发布入口全程未动，任何情况下用户侧不受影响。
